Introduction & outcomes

AI agents will become a primary way we interact with computers — understanding needs and preferences, and helping with tasks and decisions. Forward deployed work means shipping those capabilities inside a customer’s real environment: right mode, right context, hard boundaries, and a human as the merge gate.

After this material you should be able to:

  • Select the right interaction mode for any task.
  • Apply context engineering to produce consistent, reviewable output.
  • Configure behavior with custom instructions, AGENTS.md, and related files.
  • Extend the assistant with MCP tools, extensions, agent skills, prompt files, and custom agents.
  • Integrate a CLI assistant into CI/CD with access controls and approval gates.

What are AI coding assistants?

LLM-powered tools embedded in your editor that understand code structure, not just syntax:

  • Reasoning engines — they analyze intent, not just patterns
  • Context-aware — they read open files, imports, and project structure
  • Multi-modal — generation, refactoring, debugging, documentation, and review in one tool
  • Iterative — they improve through conversation, not only single-shot completion

They generate code, explain or improve existing code, help with debugging, produce documentation, and build small multi-file structures. Quality depends entirely on the instructions you provide — vague prompts produce vague code.

Architecture & components

ComponentRole
LLMReasoning and generation — processes tokens, produces output
Context managerDetermines what information the model sees for each request
Tooling layerFile access, terminal commands, Git operations
Safety & guardrailsPrevent harmful or unsafe actions
IDE / surface integrationExtension, CLI, or standalone IDE you interact with

Every assistant packages these five components differently. The integration model determines what the assistant can see and do.

Integration models

ModelWhat it means
IDE extensionAdds chat and inline suggestions to an existing editor. Operates in the editor sandbox; needs explicit permissions for terminal or Git.
Standalone CLIRuns in the terminal, reading and writing files directly. Often has full filesystem and terminal access by default.
Standalone IDEReplaces the editor — assistant wired into every surface.

Autonomy levels

  • Level 0 — Passive: autocomplete, inline suggestions
  • Level 1 — Reactive: responds to prompts, no independent action
  • Level 2 — Guided autonomy: executes steps when instructed (run tests, modify files)
  • Level 3 — Semi-autonomous: plans and executes multi-step tasks with oversight
  • Level 4 — Fully autonomous (emerging): end-to-end feature delivery with human approval at checkpoints

Most tools operate across several levels depending on mode. Inline completions are Level 0. Chat is Level 1. Permission to run commands or edit files is Level 2. Agent / composer modes operate at Level 3. Match autonomy to risk: autocomplete for small edits; agent mode for larger refactors with review at each step.

How assistants process input

The input pipeline:

  • User prompt
  • Context assembly (files, codebase, history)
  • Tokenization
  • Model inference
  • Output tokens generated
  • Optional assistant actions (file edits, commands)

Assistants do not “think” — they process text in steps. Everything is broken into tokens; the model predicts the best output one token at a time. Every step is mechanical. There is no understanding — pattern matching over tokens. The better your input, the better the patterns matched.

Context windows

The assistant can only see what fits in its context window — the maximum text the model can process at once. That includes your prompt, file contents, conversation history, and system instructions.

  • A 128K token window holds roughly 400 pages of text — about 50 source files of 200 lines each.
  • A 10-turn conversation with file references can consume 30–40% of that budget before you ask your question.

Bigger window ≠ better reasoning — but it determines how much of your codebase the assistant can work with at once. Focused prompts beat long rambling conversations. Every token wasted on vague context is a token not spent on your actual codebase.

Token limits

  • 1 token ≈ 3–4 characters
  • Models have strict token limits
  • If you exceed the limit: truncate, compress context, or refuse the request

When you hit the limit, the assistant is flying blind on whatever it dropped. Keep prompts focused and reference only the files that matter for the current task.

Truncation & compression

Truncation drops oldest or least relevant content — risk: missing important details. Compression summarizes to fit — risk: losing nuance. Your job: provide explicit references to the files or details that matter. If earlier content is removed or compressed you get missing details, incorrect assumptions, and hallucinations.

If you are several turns in and the assistant starts making mistakes it did not make earlier, context compression is likely the cause. Start a fresh conversation and re-attach the relevant files.

The plan → execute → iterate cycle

The most reliable workflow for multi-step tasks:

  • Plan — ask the assistant to outline steps before writing code
  • Execute — have it perform one step at a time
  • Iterate — review output, refine the prompt, repeat

Prevents runaway actions and keeps the developer in control. You catch mistakes at each step instead of after half the file is rewritten.

In practice

Plan: I need to add input validation to checkout in src/cart/checkout.ts.
Before writing any code, outline what validations are needed and where each check should go.

Execute: Implement the null cart check from step 1.
Use an early return that throws InvalidCartError. Don't change anything else yet.

Iterate: The null check works, but it doesn't handle an empty items array.
Add that case to the same guard clause. Keep the error type consistent.
  • Plan forces reasoning before coding — you review the plan, not the code.
  • Execute limits blast radius — one change, one review.
  • Iterate builds on real output, not guesses.

The plan prompt says “before writing any code” on purpose. Jumping to “add validation” writes code immediately and you lose the chance to shape the approach. The execute prompt names the check, the error type, and “don’t change anything else.” Without that, the assistant may “helpfully” refactor nearby code.

Why explicit planning?

  • They don’t know your intent unless you state it
  • They can hallucinate missing steps
  • They may take shortcuts
  • They benefit from structured constraints

Planning makes the workflow predictable and safe. Every major tool surfaces its plan before executing — learn what your tool does by default, and prompt for a plan explicitly when it does not. Some tools show a high-level summary for whole approval; others show file-level diffs to accept or reject individually.

Breaking tasks into steps

Instead of “Build a login system,” break into: define requirements and constraints → generate folder structure → implement authentication → add tests per module → integrate with existing code.

If reviewing a single step takes more than a minute, the step was too big. Good steps have clear boundaries, single responsibility, observable outputs, and opportunities for review.

Autonomous operations

Assistants can perform file, terminal, and Git operations. Autonomy levels vary. Always review and validate. You are the final gatekeeper. The more access an assistant has, the more damage a bad prompt can cause — treat autonomous ops the way you treat production deployments.

File operations

Read, create, modify, delete. Follow user instructions. Apply patches. Require clear paths, formats, and expected outcomes. Ambiguity leads to incorrect file changes. Before accepting any file change, name the exact file and ask for the diff. If you cannot tell what changed by reading the diff, the change is not ready to accept.

Terminal operations

Capabilities: run commands, interpret output, propose next steps, automate repetitive workflows, surface logs and errors. Constraints: assistants only “see” command output; they cannot infer environment state; they may hallucinate commands if the toolchain is unspecified. State the toolchain explicitly — “use pytest, not unittest” or “use npm, not yarn.”

Git operations

Stage and commit, generate commit messages, create branches, propose diffs and rewrites, review before applying. Treat every assistant-generated commit the way you would treat a pull request from a new team member: read every line before you merge it.

Reviewing & accepting changes

  • Inspect diffs line by line
  • Validate alignment with the request
  • Check for unintended side effects
  • Ensure naming, structure, and style consistency
  • Confirm no functionality was removed unintentionally

Common silent extras: a dynamic tax-rate lookup replaced with a hardcoded rate; a loyalty discount deleted; a cache dependency added to a simple database query without being asked. Also check whether the diff introduces dependencies or behaviors you did not request. After reviewing what changed, explicitly scan for what was removed.

Review checklist

  • Does the diff match what you asked for — and only that?
  • Were any function calls removed or replaced?
  • Are there hardcoded values that should be dynamic?
  • Does the style match the rest of the project?
  • Did variable names or return types change?

Identifying & detecting hallucinations

Common patterns: nonexistent functions or methods; wrong API signatures; fabricated file paths; outdated imports that compile against the wrong library major (for example persistence packages renamed between EE generations). Hallucinations look most dangerous when they compile successfully — a wrong import can pass syntax checks and fail at runtime.

They are not random gibberish — plausible-looking code that happens to be wrong. When something looks too clean, verify it. Ask whether that import works with your exact framework version. A good assistant corrects itself; a hallucinating one doubles down.

  • Cross-check against the codebase and library documentation
  • Ask for file or line references — if it cannot cite them, that is a red flag
  • Request self-critique — many assistants catch their own mistakes when prompted
  • Run the build and tests to validate assumptions

Hallucinations cluster around version-sensitive APIs, recently renamed packages, and framework features that changed between major releases. The training data includes all versions, so the model may confidently generate code for the wrong one.

Ensuring correctness

  • Ask for step-by-step reasoning
  • Request test cases or edge-case analysis
  • Compare multiple versions
  • Use self-critique prompts
  • Run the code and inspect logs

Correctness is never assumed — it is verified. The first answer is a draft, not a deliverable.

Security considerations

Risks in AI-generated code: hard-coded secrets; overly permissive IAM roles; unsafe input handling; incorrect trust assumptions; insecure defaults.

Best practices: specify security constraints explicitly; ask assistants to justify security decisions; request a security review of generated code. State security constraints in every prompt — the assistant does not inherit your organization’s security policies. Add “use least-privilege IAM” and “validate all inputs” as part of the specification, not as afterthoughts.

Foundations recap: LLM + context manager + tooling + safety + IDE surface. 128K tokens ≈ 400 pages ≈ 50 files; conversation history shares the budget. Plan → execute → iterate, one step at a time. Cross-check against the codebase; ask for citations. File, terminal, Git access — always review first.

Four interaction modes

One model with many surfaces. The mode you pick sets the supervision level.

ModeWhat it is
Inline completions (and next-edit suggestions)Keystroke-level autocomplete using the current file, cursor, and open tabs. Lowest supervision; review every accept in unfamiliar code.
Ask modeConversational, read-only chat. Panel chat persists across turns for multi-file thinking; inline chat (Ctrl+I / Cmd+I) is local to a selection. Use it to think, not to change.
Agent modeAutonomous execution in the IDE — reads files, runs commands, iterates on test failures. Agent logs are your supervision surface; review the diff before accepting.
Plan modeProduces a written, reviewable plan before any code is written. It asks clarifying questions, then you approve. The plan agent saves the plan to a markdown file (plan.md in session memory; *.plan.md for custom planning agents). “Start implementation” hands it to agent mode. Correcting a plan costs one prompt; correcting wrong code costs a revert.

Choosing a mode

If the task is…Use…Because…
A single line or obvious completionInline completionsCheapest surface, lowest friction
A question about code you did not writeAsk (chat panel)Conversation history and workspace context help you think
A quick explanation of the block you are looking atAsk (inline chat)Keeps the question local, no panel context to manage
A small, well-understood changeAgent mode (single turn)Executes and shows a diff; cheap to review, cheap to revert
A multi-step task where the shape is less clearPlan mode → agent modePlan catches misunderstandings cheaply; agent logs and diffs keep you in control

Context engineering

Objectives: explain how context influences output; apply context management; select reference systems (files, codebase, docs); construct prompts with structured techniques; distinguish prompting techniques from built-in extended thinking modes.

Overview

  • What context is and why it determines whether output is accurate or hallucinated
  • How to scope, ground, and reduce noise
  • Which reference systems to attach — files, codebase, documentation, and web — and when each is appropriate
  • Zero-shot, few-shot, and structured prompting for reliable, reproducible results
  • How prompt-driven reasoning differs from built-in extended thinking, and when to use each

What is context?

  • Everything the assistant uses to interpret your request
  • Reusable prompts (instructions, rules) set standing behavior
  • Context interfaces (tools, MCP, file references) connect to live artifacts
  • Workspace files (code, configs, docs) supply the material reasoned over

Together these determine how the assistant frames the problem. When a response hallucinates an API or invents a function signature, the root cause is almost always missing context — the assistant filled the gap with plausible fiction.

Types of context

  • Instructional — shapes what the assistant does; write instructions it can follow literally
  • Reference — grounds in real artifacts; attach files, codebase, or docs to eliminate guesswork
  • Conversational — carries prior decisions; restate constraints that must survive across turns
  • Environmental — exposes tools and repository state the assistant can act on

Context can be LLM-initiated (the assistant searches), human-initiated (you attach a file), or loaded by agent software (configuration files, MCP servers). Knowing which type helps you decide where to invest effort. Most developers default to instructional context only. Real gains come from combining all four.

Why context matters

Most assistant failures trace back to missing or vague context.

Weak vs strong

Weak: Fix the bug in the login function.

Strong: The login function in auth/login.ts returns 200 even when
bcrypt.compare resolves to false on line 42. The response sends before
the await completes. Fix the race condition.
Start every prompt by attaching the file you want changed — the rest of the context flows from there. When the assistant invents an API or misses the bug, ask first: “Did I give it enough to work with?”

Prompting techniques

  • Zero-shot — simple, unambiguous tasks where expected output is obvious
  • Few-shot — 2–3 examples so the assistant imitates format and style
  • Structured prompting — step-by-step workflow instructions for complex tasks
  • Reference-based — attach files, code, or docs
  • Stepwise — break large tasks into atomic requests

Match the technique to the task. A simple rename is zero-shot. A multi-file refactor with strict formatting needs few-shot examples and file references.

Zero-shot

No examples. Assistant infers structure from the request. Best for simple, well-defined tasks.

Add a validate_email function to utils/validators.py that returns True
if the input matches RFC 5322. Use the re module. Return a bool.

Few-shot

Provide examples of desired behavior. Useful for formatting, style, or domain-specific tasks. Two or three examples are usually enough.

Convert these to snake_case:
- getUserName → get_user_name
- setPageTitle → set_page_title
- fetchOrderById → ?

Generate docstrings following this pattern:
Example input: def add(a, b): return a + b
Example output: """Add two numbers..."""
Now generate a docstring for: def calculate_discount(price, rate):

Reference systems

Assistants can read and reason over files, codebases, documentation, and web content (when allowed). Attaching real artifacts is the fastest way to eliminate hallucinations.

Attach a file

Most precise grounding. Use for bug fixes, refactoring, documentation. Without it, the assistant guesses signatures, names, and imports.

Search the codebase

Use for architecture summaries, dependency tracing, multi-file changes. Some tools need an explicit keyword (@workspace, #codebase); agent tools may search automatically.

Attach documentation

Use for API alignment, requirements, constraints. Without a spec, the assistant invents endpoints, field names, and status codes.

Fetch web content

Use for library docs, standards, examples that post-date training data. Be selective — a focused SDK reference works; a sprawling tutorial site introduces noise. Not every product supports fetch.

Reasoning techniques

Two categories:

  • Prompting techniques — you guide reasoning (chain of thought, deliberate reasoning). Universal.
  • Extended thinking — architectural features built into some agents that enable a deeper pass before responding. Tool-specific; costs extra time.

Chain of thought

Step-by-step reasoning. Useful for logic, algorithms, debugging. Reveals hidden assumptions. Ask the assistant to walk each branch and show where a return is missing.

Deliberate reasoning

Ask for multiple candidate solutions, compare (latency, invalidation, cost), choose the best. The first solution is rarely the best — alternatives force tradeoffs the model would otherwise skip.

Risks and verification

  • Reasoning steps can be fluent but wrong — verify each step against the actual code
  • A hallucinated logic chain reads authoritatively even when it rests on a false premise (e.g. assuming sync when it returns a Promise)
  • Compressed history causes misinterpretation of earlier constraints
  • Hidden assumptions get stated as facts — name the failure modes you care about
Never trust a reasoning chain at face value — always verify each step against the actual code.

Self-critique

Asking the assistant to critique its own output surfaces mistakes it would otherwise ship. Naming specific failure modes (size limits, path traversal, timeout behavior) gets actionable findings — a generic “any issues?” does not.

Review the upload handler you just wrote.
Check for: missing file size limits, path traversal in the filename,
and what happens if object storage returns a 503.

Memory & persistence

What gets lost: the schema you described 30 messages ago; the constraint that the API must stay backward-compatible; the specific error from your last test run.

How to prevent it: restate constraints in each new prompt; re-attach key files instead of relying on history; keep conversations focused — start a new session for a new task; use configuration files for persistent project rules.

Start a new session for each new task — stale context from a previous task is the most common source of silent drift. Assistants have no long-term memory. Do not trust the assistant to remember.
Context recap: Context determines output quality. Zero-shot and few-shot fit different complexities. Chain-of-thought and extended thinking are distinct. Reference systems ground responses. Always validate — think in probabilities, not guarantees.

Modes have different contexts

There is no single context model. What the assistant sees depends on the mode you pick. Effective prompting is knowing which sources are active right now and putting the right things in them.

ModeContext sourcesWho chooses them
Inline completionsCurrent file, cursor, surrounding code, open tabs, importsMostly implicit (what you have open)
Ask modePrompt, conversation history, attached files, codebase when invokedYou (explicit opt-in)
Agent mode (IDE)Autonomous file reads, terminal output, compiler/linter feedback, anything you attachMostly the agent (your goal as the anchor)

Debugging a disappointing output

When the assistant misses, identify which row of the table you were in and ask whether those sources actually contained what was needed.

  • Ask: context quality is your responsibility. Wrong or shallow answers usually mean the relevant code, file, or constraint was never in the prompt — adding it is the fix.
  • Agent: the agent chooses most of what it reads, but your goal and starting workspace state anchor everything. If it drifted, revisit how you framed the goal, then check agent logs for which files it read before each change.
  • Inline: context is almost entirely implicit. Close unrelated tabs and keep the relevant file in focus.

Configuration standards

Objectives: differentiate configuration hierarchy levels and behavioral files; create project-level configs that encode team norms; apply file exclusion; design safe, predictable assistant behavior.

Why configuration matters

Configuration files define how an assistant is allowed to act inside a project. They create a shared understanding of boundaries, tone, and responsibilities. Think of configuration as infrastructure — it sits alongside source files in version control. Every developer who clones the repository inherits the same behavioral contract.

  • Predictability — two developers asking the same question get equivalent output
  • Safety — the assistant is blocked from deleting migration files even when explicitly asked
  • Reproducibility — a new team member gets identical assistant behavior from day one

Without these files, every developer gets a slightly different assistant — different tone, assumptions, and risk tolerance. Configuration eliminates that drift. Diff it in pull requests; roll it back if something breaks.

Common configuration files

  • Behavioral configs — define persona, tone, and hard boundaries for a project
  • Multi-agent configs (e.g. AGENTS.md style) — assign distinct roles and responsibilities
  • Project-level path constraints; operation allowlists and denylists

These files outlast any single prompt or chat session. Once committed, they govern every future interaction in that project.

Behavioral configuration

Different tools, same concept — a file in the repository that defines persona, constraints, and allowed operations. Typical location patterns: project root instruction files, editor rule files, or a dedicated instructions folder in the repo. Content includes tone, role and expectations, allowed vs disallowed actions, safety constraints, communication style. Treat it as the assistant’s job description.

# Project: payments-api
You are a backend developer working on a Python FastAPI service.
Use snake_case for all functions. Follow PEP 8.
Never modify files in the /migrations directory.
Always include type hints on function signatures.
Run pytest before suggesting a commit.

Multi-agent configuration

Define multiple roles, each with boundaries: developer (writes), reviewer (critiques, may not edit), tester, architect. Separation of concerns: a reviewer that cannot edit produces more honest reviews. When each agent has a well-defined role and hard boundaries, the system behaves more like a real team.

Advanced patterns & safety constraints

Basic configuration tells the assistant how to behave. Advanced patterns tell it what not to touch and how to fail safely: safety constraints, file exclusion, least privilege.

  • Restrict dangerous operations
  • Enforce least-privilege behavior
  • Prevent unintended file writes
  • Limit scope of autonomous actions

When a constraint fires: complete the safe portion, explain why it stopped. Partial completion with transparency — not silent failure or blind obedience.

Write safety constraints as “never” rules — harder for the assistant to rationalize away than “avoid” or “prefer not to.”

File exclusion strategies

Exclusion patterns keep the assistant focused on source code and away from noise. Use gitignore-style syntax.

  • Build artifacts — node_modules/, dist/, bin/, target/ — large and irrelevant
  • Secrets — .env, API keys, credential files, tokens — must never appear in assistant context
  • Generated output — coverage, caches — adds noise, no value
Secret exclusion is a security requirement, not a convenience — if the assistant can read a .env file, it can echo credentials in a suggestion.

Encode the decision in configuration so it applies to every developer on the team.

Model Context Protocol (MCP)

Objectives: describe MCP architecture and purpose; explain tools, resources, and prompts; identify security and permission considerations; evaluate when MCP is appropriate.

What is MCP?

A standard protocol for connecting AI assistants to external tools. It defines how assistants discover and use capabilities and enables structured, predictable interactions — discovery, invocation, response handling, and error reporting.

The problem: fragmentation

Before MCP, every assistant–tool integration was a one-off: custom plugins, bespoke APIs, one-off scripts. Adding a new tool meant separate glue for each assistant. No shared schema for tool definitions, errors, or request formats. Debugging meant reverse-engineering each integration. MCP eliminates this with one schema, one request/response format, one error approach.

What MCP enables

  • Write a tool server once; use it from any MCP-compatible assistant
  • Common JSON Schema for tool definitions, inputs, and errors
  • Swap assistants without rewriting integrations
  • Predictable debugging: inspect a standard request/response pair

MCP architecture

flowchart LR Dev[Developer] --> Host[Host app] Host --> Client[MCP client] Client --> Srv[MCP server] Srv --> Tools[Tools] Srv --> Res[Resources] Srv --> Prompts[Prompts]
  • Client — the assistant or host that discovers and invokes capabilities
  • MCP server — declares tools, resources, and prompts; runs as trusted code
  • Tools — actions (API calls, queries, file operations)
  • Resources — read-only context (files, docs, config)
  • Prompts — predefined templates for consistent workflows

The server declares what is available; the host decides what to allow. MCP servers run with OS-level permissions — not sandboxed by the protocol. Confusing those two is the most common MCP security mistake.

Configuring a server

Each host uses its own config file. Typical pattern: a command executable plus args; the host starts the server, connects over stdio, and discovers tools. The server binary is the same regardless of which host launches it — only the config format differs.

What a tool declaration looks like

{
  "name": "query_database",
  "description": "Run a read-only SQL query",
  "inputSchema": {
    "type": "object",
    "properties": {
      "query": { "type": "string" },
      "database": { "type": "string" }
    },
    "required": ["query", "database"]
  }
}

The model reads description to decide when to call the tool. Clear, specific descriptions improve tool-selection accuracy. inputSchema uses JSON Schema so inputs can be validated before the call.

Security, permissions & observability

  • Protocol — message formats and tool declarations; no built-in auth, encryption, or sandboxing
  • Server — declares tools; runs as trusted code with OS permissions
  • Host — enforces permission boundaries, controls invocation, implements human-in-the-loop approval
The protocol moves messages — the host decides whether those messages should be allowed to execute. Never treat MCP itself as a security layer.

Least privilege: grant only the minimum required capabilities; avoid broad unrestricted tools; reduce blast radius; improve auditability. A database server that only needs schemas should not expose “run arbitrary SQL.”

Defense in depth example: developer asks to drop a table → server only exposes read-only tools → assistant cannot comply because no destructive tool exists → even if a drop tool were added later, the host would show a permission prompt. Both layers would have to fail for data loss.

Observability: log tool usage; keep traceability of assistant actions; support audits and debugging. In regulated environments, answering “which tool, with what inputs, what came back?” is not optional.

When to use MCP

If you are copy-pasting the same external data into assistant conversations repeatedly, that is the workflow MCP was designed to replace.

Use when: live external data (databases, APIs, cloud resources); same tool across multiple assistants; safety, permissions, and audit trails matter; reproducibility across users and environments.

Skip when: simple prompt with no external tooling; built-in features already cover it; you only need file context (use file references instead).

Real-world scenarios

  • Documentation grounding — index API docs so generated code matches real endpoints
  • Database access — read-only schema and sample queries without write access
  • CI/CD integration — retrieve build logs and test results to diagnose failures
  • Cloud resource queries — read resource metadata for infrastructure-aware generation

Invocation flow

Developer asks a natural-language question → model selects a tool → host shows a permission prompt → server executes and returns results → assistant may chain additional calls → compose the answer. Assistants rarely answer complex questions with a single invocation — they iterate.

Notable server types

  • Version-specific library documentation (reduces hallucinated APIs)
  • Repository / issues / pull-request access
  • Scoped filesystem with configurable read/write boundaries
  • Read-only SQL databases for schema exploration
  • Browser automation for UI testing and scraping workflows

Before building a custom server, check the ecosystem — most common needs already have maintained servers ready to configure.

Practical workflows for developers

Objectives: structured prompting for generation, scaffolding, and debugging; refactor, document, and automate Git; modernize legacy code incrementally; integrate output safely; generate targeted tests; conduct assistant-driven reviews focused on correctness and risk.

The recurring theme is control. You set direction, define constraints, and verify output. The assistant handles mechanical work in between.

Code generation — clear requirements

Assistants behave like junior developers: they do best when they fully understand the problem. Good requirements include what the function should do, input/output formats, edge cases or constraints, and examples.

Write a REST endpoint in src/api/orders.ts that accepts POST /orders
with customerId (string) and items (array of {sku, qty}).
Return 201 with the created order ID. Validate qty > 0.
Use the existing db.insert() from lib/db.ts.

Prompt pattern: good → better → best

  • Good — what you want
  • Better — inputs/outputs + constraints
  • Best — examples + acceptance criteria + guardrails (“don’t change X”)
GOOD: Write a Python function to validate an email.

BETTER: Write validate_email(email: str) -> bool. Reject missing @,
missing domain, spaces. No external deps.

BEST: Write validate_email(email: str) -> bool.
Constraints: no external deps, <25 lines, PEP8.
Acceptance: 8 pytest cases (normal + edge + invalid).
Guardrails: don't change existing signatures in utils/validation.py.

When the assistant drifts, the prompt usually lacked a concrete definition of done. Add acceptance criteria like “tests pass,” “returns X on Y,” “no new dependencies,” “only modify file Z.” Make the assistant restate requirements before coding.

Constraints & acceptance criteria

Performance, security, style/architecture, testability, definition of done. Without constraints, the assistant optimizes for “plausible code”; with constraints, it optimizes for code that fits your system. Define “done” before you generate code.

Multi-file scaffolding

Folder structures, initial modules, interfaces, and stubs can be generated in one prompt. Specify naming and module boundaries first. Workflow: generate → review the diff → integrate — keeps each step reversible. Scaffolding is where assistants save the most time and introduce the most risk — review every generated file.

Ask for structure + rationale first; then scaffolding only (placeholders); keep it small: max files, flat layout, no rewrites.

Designing folder structures

Organize by feature or layer; keep modules cohesive; avoid deep nesting; align with team conventions. Let the assistant propose and explain, but validate against your team’s actual conventions before accepting any restructure.

Modular code patterns

Separation of concerns, reusable components, clear interfaces, dependency minimization. Assistants default to “make it work” — your job is to enforce “make it modular” by telling which boundaries matter before generation (validator / pricing / payment / notification; thin orchestrator).

Debugging with assistants

Structured investigation, not just “fix the bug”: log interpretation → hypothesis generation → diagnostic steps → iterative narrowing.

Log interpretation

Extract key errors, identify failure points, propose likely causes, suggest next diagnostic steps. Confirm conclusions against the raw output before acting.

Hypothesis generation

Propose multiple root causes; rank by likelihood; suggest targeted tests; avoid premature conclusions. Asking for three ranked hypotheses before changing code keeps you from chasing the first plausible explanation.

Stepwise debugging

Reproduce → inspect logs and state → apply minimal fixes → retest and iterate. Saying “step 1 only” keeps the assistant from jumping to a fix before you understand the root cause.

Integrate output safely

  1. Diff review — what changed and why? Watch for new dependencies, changed interfaces, unsafe calls.
  2. Run checks — tests, lint, type checks.
  3. Commit — small, reversible commits with messages that capture intent.
When the assistant changes more files than you expected, revert and re-prompt with a tighter scope instead of reviewing a large diff.

Checklist: diff reviewed; tests run; no new secrets/keys; no widened permissions; commit message captures intent.

Refactoring workflows

Refactoring improves structure without changing behavior. Incremental small-diff changes are safer than large rewrites. Behavior preservation is non-negotiable — every refactoring prompt should include it explicitly.

  • Ask for a plan first
  • Require behavior identical
  • Request output as a unified diff
  • Validate with tests immediately

If refactoring changes behaviour, it wasn’t refactoring — it was rewriting. If a module has weak/no tests, generate minimal tests first. A refactor that touches 200 lines is a rewrite — ask for small diffs, review each one, run tests between steps.

Identifying smells

Long functions, duplicate logic, tight coupling, poor naming, dead code. Require the assistant to cite line ranges and name the pattern — generic “this could be improved” is not actionable.

Suggesting improvements

Simplify logic, improve naming, extract functions, reduce dependencies, increase readability. Asking for a plan before code gives you options to evaluate — then ask for implementation.

Documentation generation

API docs, inline comments, architectural summaries, onboarding materials. Add the guardrail “only describe behavior visible in the code” to prevent inventing functionality. If anything is ambiguous, add a note with a question instead of guessing.

API docs

Function descriptions, parameters, return values, error conditions. Point the assistant at the code and the existing doc format.

Avoid invented details

Specify doc style; require “only based on code shown”; ask for assumptions + edge cases + errors. The most common documentation failure mode is confident invention. Treat generated docs like generated code: review critically.

Inline comments

Explain complex logic and intent; highlight assumptions; avoid restating obvious code. Best comments explain “why,” not “what.”

Architectural summaries

High-level overview, module relationships, data flow, key responsibilities. Only describe what is visible; flag unclear modules. Verify against the actual dependency graph before sharing.

Git automation

Generate commit messages from staged diffs; create branch names from ticket descriptions; produce PR descriptions with rationale and risks; summarize multi-file diffs. Git artifacts create traceability. Every generated Git artifact should be reviewed before it leaves your machine.

Commit messages

Summarize changes, not files touched. Follow Conventional Commits or team format. Explain the “why” in the body. Reference ticket numbers. First line under 72 chars, imperative mood. The diff already shows what — the body should focus on why.

Branch creation

Follow team naming: type prefix, ticket number, short description. Give the convention once in a configuration file and it will apply every time. Consistency across the team matters more than saving seconds on one name.

PR descriptions

Summarize changes and rationale; list testing performed; highlight risks and mitigations; include rollback plan; reference related issues. Verify every claim — especially “tests pass” and “no breaking changes.” If claims are not backed by evidence: rewrite using only the diff summary, tests you ran, and observed outputs. Remove assumptions.

Advanced workflows — testing, review, modernization

Checking correctness is a core skill: real-world software quality depends more on tests and review than on initial implementation. Assistants accelerate validation; you remain the quality gatekeeper.

Unit tests

  • Each unit test targets a single function in isolation
  • Edge cases must be explicitly requested — the assistant does not infer them
  • Predictable behavior is confirmed through assertions, not assumptions

Provide: clear function signature, expected behavior, edge-case scenarios, framework, and mocking strategy. Good unit tests come from good specifications.

Integration tests

Verify interactions between modules; validate data flow; catch interface mismatches; ensure end-to-end behavior. Tell the assistant which boundaries are real and which should be mocked.

Mocking strategies

Replace external dependencies; control the test environment; simulate APIs, databases, services. Tell the assistant exactly what the mock should return, when it should throw, and how to inject it. Vague mocking instructions produce mocks that hide real bugs.

Assistant-driven code review

Identify issues and smells; highlight risky patterns; suggest improvements; provide rationale. Use as a first-pass reviewer for mechanical issues (naming, null checks, missing error handling) so humans can focus on design and intent. Assistants do not understand domain context unless you provide it.

Review prompts

Ask for structured reviews, line-by-line analysis, risk-focused feedback, alternative implementations. “Review this code” produces generic feedback; “check this auth handler for SQL injection and missing rate limiting” produces actionable findings. Rate findings: critical / warning / nit.

Risk identification

Security, performance, maintainability, hidden assumptions. “What risks do you see?” is one of the highest-value prompts — it forces a scan across security, performance, and correctness simultaneously.

Assistants accelerate quality workflows — you ensure the quality is real. You decide which findings matter, which tests are correct, and when the code is ready to ship.

Modernizing legacy code

Assistants excel at mechanical, repetitive migrations: API upgrades; language modernization; pattern migration (callbacks → async/await); dependency updates. Run the full test suite after every transformation — edge cases around serialization and reflection can break silently.

Java modernization patterns

  • Collections.unmodifiableList() → stream toList()
  • instanceof + cast → pattern matching
  • Anonymous classes → lambdas and records
  • Legacy date APIs → modern date/time formatters
  • Switch statements → switch expressions with arrow syntax

The assistant handles mechanical translation — you verify JVM version, library compatibility, and deployment constraints.

.NET modernization patterns

  • Verbose project files → SDK-style projects
  • Legacy HTTP clients → modern HTTP client factories
  • Older ORM stacks → current ORM with async patterns
  • Sync data access → async/await
  • Legacy web dependencies → modern middleware

Assistants can outline a migration plan and rewrite classes — they cannot verify environmental compatibility. That requires running the application and its tests against the target runtime.

Transformation & safety

  • Preserve behavior
  • Avoid breaking changes
  • Validate assumptions
  • Apply incremental updates

Tell the assistant: “Preserve behavior.” “Do not introduce new features.” “Apply only these changes…” Without that phrase, the assistant will opportunistically modernize anything it notices.

Large-scale changes

Apply consistent patterns across files; update many files in one pass; maintain architectural integrity; use generated diffs. Repetitive multi-file changes are a sweet spot — but large changes magnify risk. Review every change carefully. Assistants scale your reach; you protect system integrity.

Validating transformations

  • Run tests
  • Compare old vs new behavior
  • Request assistant self-critique
  • Document why the modernization occurred

Self-critique catches issues before you compile, but it is not a substitute for running tests. Modernization is not complete until behavior is verified.

Assistant features & surfaces

Objectives: select an appropriate model family and surface; apply agent mode and the cloud coding agent; use Spaces, extensions, and the agents window; configure workspace indexing and instruction files; run the CLI in non-interactive mode inside a pipeline with security controls.

Model selection

Several model families typically appear in the picker, shared across chat, plan mode, and agent mode. Pick deliberately by task — families behave differently under load.

Family profileReach for it when…
General-purpose defaultWell-rounded coverage; broad tasks
Multi-step reasoningComplex refactors, plan agent, hard reasoning
Alternate family (plan/region gated)Your plan exposes it and the task profile fits

Plan tier gates the list. Org admins can further restrict. Treat the picker the way you treat any model choice — pick by what the task needs, not by what feels biggest.

Optimizing model choice

  • Reasoning-leaning — plan agent, hard refactors
  • Speed-leaning — completions, quick ask turns
  • Balanced — general-purpose default

Avoid the “always pick the biggest” reflex — premium reasoning on a small completion is overhead, not value.

Usage metering (credits)

Higher-cost usage is often metered by token consumption (input, output, cached) at per-model rates — not flat per-request units. Typically metered: chat, plan mode, agent mode, code review, CLI, coding agent. Often not metered: inline completions and next-edit suggestions. When the allowance is spent, premium features stop until you buy more or the cycle resets; inline completions may keep working. Admins can set budgets and caps. Credit burn is driven by both model choice and context size.

Spending habits

  • Free surfaces first — lean on inline completions for routine code
  • Match the model to the task
  • Scope the context — fewer tokens in means fewer credits out
  • Plan before you act — a wrong agent run spends credits twice; catching it in plan mode costs one prompt

The cheapest credit is the one you never needed to spend. Long unattended agent loops with broad context are a common source of surprise burn.

Chat panel

Persistent across turns; workspace-aware when scoped; chat participants (terminal, editor, platform); slash commands (explain, fix, tests, doc, new). Best for multi-file questions and multi-turn investigation. Treat it as a working conversation with attached context and follow-ups — not a search box.

Inline chat

Floating prompt anchored to selection (Ctrl+I / Cmd+I). Ephemeral — no history across invocations. Best for local questions you act on once. The panel remembers; inline chat does not.

Plan mode

Describe the goal, answer clarifying questions, review the plan, approve. Plan artifact written to markdown. No edits. “Start implementation” hands off to agent mode. Older multi-file edit surfaces are deprecated — that role moved into agent mode. Plan mode → agent mode is the path forward.

Agent mode

Contract: goal in, diff out. Workspace actions: read files, run terminal commands, propose diffs. Agent logs are your supervision surface. Diff review: the assistant proposes; you approve. Pair with plan agent. Also handles coordinated multi-file changes. Students who skip logs and diffs produce green suites that hide broken code.

Agents window

Dedicated window for agent-first, multi-project work: sessions grouped by project; customizations (custom agents, skills, instructions, hooks, MCP servers, plugins); chat; changes tabs with diffs; session controls; commit / merge / checkout / discard. Best for many sessions, one supervisor.

The cloud coding agent

Lives on the platform rather than the IDE. Asynchronous, sandboxed work whose result the team reviews as a PR. Initiated by assigning an issue or prompting on the web. Structural sandboxing (branch protections, controlled network, approval gates) makes useful autonomy safe without granting keys to production.

Execution loop

  • Research — read the repository
  • Plan — outline the implementation
  • Commit — push to a draft PR
  • Self-review — run automated review on the diff
  • Security scan — before requesting review
  • Request review — hand off to a human

Merge is never automatic — the final step is always human review.

Supervision

  • Session logs — cloud-side agent logs
  • PR review comments — in-loop feedback channel
  • Branch protections — by design; CI/CD needs human approval
  • Model picker — by task complexity

Structural gates rather than operator-dependent ones — the safety envelope holds even when “the operator forgot” is the failure mode.

Spaces

Curated, named context collections. Reference a Space to load its bundle into chat or agent mode: files and references, Space-specific instructions, named and shareable, cumulative on top of the mode’s normal context. Solves reassembling the same bundle by hand each time.

SurfaceWhat it encodes
SpaceReusable context bundle — files, references, ad-hoc instructions for a kind of work. Loaded when referenced.
Prompt fileReusable prompt — what to ask in a specific situation. Invoked as a slash command.
Repo instructions fileAlways-true rules for the repository. Loaded on every turn.
Path-specific instructionsRules scoped to a directory or language via applyTo globs.

Ask: is this what I want considered, what I want asked, or what should always be true? The right surface follows.

Extensions, plugins & custom agents

Third-party chat participants appear as @name in chat. Installed at org or account level. Chat-context access when invoked. Discoverable in the marketplace.

Trust model

Treat like any third-party OAuth application: review scopes at installation; audit usage on a cadence; remove what you do not use; org-level controls restrict what can be installed. Chat-context access is equivalent to a SaaS integration seeing what you paste.

ConceptWhat it is
ExtensionsThird-party chat participants. Cross-organization. Reach outside the team.
CLI pluginsInstallable packages that bundle MCP servers, agents, skills, and hooks for the CLI. Local terminal tooling.
Custom agentsSpecialized agent configs (e.g. .agent.md). Scoped to a repository. Reviewed like other config.

Short mental model: extensions reach outside the team; plugins reach inside the terminal; custom agents reach inside the repository. Trust models follow from the reach.

Workspace indexing

ModeWhat it is
Remote indexServer-side index of the repository. Fastest and most complete. Production-quality experience.
Local indexBuilt on the engineer’s machine when remote is unavailable. Less complete; depends on local resources.
Basic indexLightweight in-IDE retrieval over open and recently edited files. Fine for small workspaces; degrades as the repo grows.

Active mode is set by organization policy — engineers do not choose it per turn. Two people, same query, different quality often means different index modes. Codebase search quality follows the active index. Remote indexing means the platform holds the index — often a data-residency conversation. Confirm residency requirements, enable remote indexing, then exercise workspace-scoped features against a real repo before broad rollout.

Configuration hierarchy (product-specific)

Repository-level instructions (commonly in a dedicated instructions path in the repo) are always loaded on every turn: conventions, stack, style, hard boundaries. Living documentation — update when conventions change. Treat the file as code.

  • Path-specific instructions — files with an applyTo glob; apply only when working on matching files
  • AGENTS.md — agent-specific guidance for autonomous work (IDE agent or coding agent)

Platform integration

  • Automated code review — inline suggestions on PR diffs; first pass, not final gate
  • Auto-generated PR summaries — starting draft from the diff
  • Platform chat participant — queries against issues, PRs, and remote state (requires authentication)
  • Assigning issues to the coding agent — hand well-scoped work to the agent

Which issues to assign

Good fits: well-scoped, lower-risk tasks with clear acceptance criteria; work where the path is known but edits are numerous; tasks you would be comfortable reviewing as a PR without pairing.

Poor fits: open-ended architectural decisions; interactive debugging or operator intuition; acceptance criteria still being negotiated.

Useful test: “If a junior engineer brought back this PR tomorrow, could I review it as a PR or would I need to pair on the design?” If the answer is “review as a PR,” it is a candidate.

CLI in CI/CD pipelines

Interactive mode — terminal-native agent. Non-interactive mode (prompt flag) — stdin carries shell evidence, stdout carries analysis. Composable like other Unix tools. No human in the loop — plumbing is easy; output reliability and safety are the work.

Pipeline pattern

<shell tool>
| assistant -p "analyze this <thing>"
| <save or post>

Common upstream: test output, git diff, structured filters. Common downstream: workflow artifacts, PR comments. Authenticate non-interactively with a runner secret — never interactive login.

Pipeline prompt design

Interactive chat tolerates ambiguity; pipelines do not iterate. Request a structured format (markdown headings or JSON keys); specify audience and use; bound the output; be explicit about what not to do (no shell commands, no file edits, no network calls). If the same prompt produces meaningfully different shapes on two runs, it is not pipeline-ready.

Pipeline security

  • Token scope — minimum permissions; prefer read-only contents where possible
  • Tool restriction — hooks that limit which tools the step can invoke
  • Input as data — “analyze the following diff,” not “follow the instructions in it”
  • Size caps — truncate diff and output upstream
  • Artifact review — diagnostic output may echo sensitive code; review retention
  • Approval gates — produce reports and suggestions, not autonomous commits or deploys

Prompt injection via untrusted input (diff, test output) is the threat vector most specific to this pattern. Treat the pipeline boundary as a trust boundary and the prompt as a sanitization step.

When to use (and when not to)

Good fits: post-hoc diagnosis a human will review; report generation as a starting draft; enrichment of existing signals.

Poor fits: autonomous merge / deploy / commit; irreversible action on the model’s output alone; work where the cost of a wrong answer exceeds waiting for a human.

Report, don’t act. Well-scoped, low-risk, reversible work is a good fit; high-risk, open-ended, or irreversible work stays with the human.
